Ziel (Definition of Done):
- Campaign/Projekt kann optional eine Unterstuetzen-Seite haben.
- Nutzer:innen koennen Pledges anlegen und erhalten Zahlungsreferenz (`CF-xxxxxx`).
- Admin kann Pledges auf `paid|canceled` setzen.
- Oeffentliche Fortschrittsanzeige funktioniert.
- Harte Regel: Unterstuetzen beeinflusst niemals Votes/XP/Credits.

Aufgaben (max 6):
1) Branch/Arbeitslage
   - Wenn dirty: Snapshot-Branch `wip/pre-pr-0030-<YYYYMMDD-HHMM>` erstellen und committen.
   - Arbeitsbranch: `e150/pr-0030`.

2) Datenmodell + API (MVP, ohne Payment-Provider)
   - `SupportCampaign` und `SupportPledge` in bestehende Campaign-Struktur integrieren (bestehende DB-Patterns nutzen).
   - Endpunkte:
     - `POST /api/support/campaigns` (owner/staff)
     - `GET /api/support/campaigns/[slug]` (public, anonymisiert)
     - `POST /api/support/campaigns/[slug]/pledges` (paymentReference zurueckgeben)
     - `GET /api/admin/support/campaigns`
     - `GET /api/admin/support/campaigns/[id]`
     - `PATCH /api/admin/support/pledges/[id]` (`paid|canceled`)
   - Keine Membership-/Bankdaten-Refactors.

3) Public UI + Campaign-CTA

   - Nach Anlage: klare Zahlungsinfo + Verwendungszweck (`CF-xxxxxx`).
   - Auf `/campaign/[id]`: `Unterstuetzen` CTA wenn Support aktiv.

4) Admin UI fuer Verbuchung/Monitoring
   - Neue Seiten:
     - `/admin/support`
     - `/admin/support/[id]`
   - Tabellen/Filter: waiting_payment, paid, canceled.
   - Aktion: `mark paid` / `cancel`.
   - CSV-Export fuer Pledges.
